# Publish the test run: $0

Arguments: $ARGUMENTS

Run folder state: !`ls -1 "$0"`

## How the dashboard works
A feature-test run is a folder (`<feature>/<area>/test-runs/<run>/` with `steps.md`, `logs/`, `scenarios/s<N>-<slug>/{videos,screenshots,data}`, `data-setup/`, optional `db-snapshots/`), next to `../../test-plan.md` and `../../bugs/<slug>/`. The dashboard shows it from one index file, `<run>/test-run.json`, that three skills fill in together: `/publish-test-plan`, `/publish-data-setup` and `/publish-test-run` (this one). Each skill owns some keys and leaves all other keys exactly as they are. The dashboard reads the run folder live (a reviewer's verdict on a scenario is pinned to its evidence list and step text, so changed evidence shows as "updated since your verdict"); there is nothing to upload and nothing to commit.

Paths inside the index are refs, `alias:relative/path` with the alias a key of `roots`, no leading `/`, no `..` segment. Standard roots: `{ "run": ".", "plan": "../..", "bugs": "../../bugs" }` (relative to the run folder). Adjust them when the plan or the bugs live elsewhere (ask unless `--auto`). Examples: `run:scenarios/s1-truncation/videos/e2e-test-1-truncation-1.mp4`, `bugs:change-summary-contact-risk-raw-json/change-summary-contact-risk-raw-json.md`.

## Rules
- Resolve `$0` to an absolute run folder first. The only file you write is `<run>/test-run.json`, through `<run>/test-run.json.tmp` and `mv`. Never write any other file in the run folder, never commit or stage anything, never touch application code, never edit `steps.md`, logs or bug files.
- Merge, never overwrite: read the existing `<run>/test-run.json` (if any), change only the keys this skill owns (below), keep every other key and unknown field as it is. In particular never change a scenario's `id`, `title` or `order`, and never touch `overview` panels the plan skill owns (`Plan summary`, `Test split`) or `dataSetup`.
- With `--auto` in the arguments or `AI_REVIEW_HEADLESS=1` set, never wait for user input: skip step 0 and take your recommendations.
- Report only what the run's files say. If a scenario's result is not in any file, its status stays what it was (or `planned` when new); never guess a verdict.

## Keys this skill owns
- Per scenario (matched by id, `S<N>`): `status`, `layers[]` (when the run reports per-layer results), `steps` (action/expected/observed/result), `evidence` (`videos`, `screenshots`, `data`), `logs` (excerpts), `links.gaps`, `links.bugs`, `notes`.
- Run level: `gaps[]`, `bugs[]`, `logs[]`, `roots.bugs`, `pages` (add `gaps` when there are gaps or bugs, `logs` when there are logs; never remove `data-setup`), `updatedAt`.
- `overview` panels titled `Results`, `Layer results`, `Run notes and deviations`, `Scenarios` (replace those by title, keep other panels; panel order: `Plan summary`, `Test split`, `Results`, `Layer results`, `Run notes and deviations`, `Scenarios`).
- `publishedBy.run` = `{ "at": "<ISO now>", "hashes": { "<key>": "<value>" } }` (see "Hashes").

## Index skeleton (when no `test-run.json` exists)
`{ "schemaVersion": 1, "runId": "<run folder name>", "title": "<run folder name>", "feature": "<folder two above test-runs/ or null>", "area": "<folder above test-runs/ or null>", "createdAt": "<ISO now>", "updatedAt": "<ISO now>", "publishedBy": {}, "roots": { "run": ".", "plan": "../.." }, "pages": [], "overview": [], "scenarios": [] }`. Without a plan-published index, create the scenarios from the scenario index table of `steps.md` (`id` `S<N>`, `title`, `order` = position, `status` from the result) and suggest `/publish-test-plan` for the step text.

## Reading the run (tolerate irregular runs)
- **Scenario ids.** The run's scenario table in `steps.md` (a "Scenario index" table with rows `S1`, `S2`, ... and a column per layer such as L1-2, L3, L4 E2E) is the primary source. `steps.md` may have no `## S<N>:` headings, and the per-step detail may live in `logs/*.md` (for example `logs/layer4-e2e-results.md`, `logs/layer1-2-results.md`) or only in the plan. Use whichever file has the text for a scenario, and take the plan's steps when none has.
- **Folder names.** Map `scenarios/*` folders to scenarios by the `S<N>` number in the folder name, case-insensitive: `s9-tables`, `S9-clean` and `_s5-superseded` all belong to `S5`/`S9`. When two folders map to the same scenario, the one without a leading `_` is current; a `_`-prefixed or `-superseded` folder is old evidence: do not list it, and when it is the only folder of that scenario, set `status: "na"` and a `notes` line "superseded" with the reason if a file gives one. Folders that match no scenario id are ignored and listed in the final report.
- **Status.** Map the run's words to `pass`, `fail`, `uncertain`, `gap`, `na`, `blocked`, `planned`: PASS/green is `pass`; FAIL/red is `fail`; "GAP-CONFIRMED", "confirmed gap", "known gap" is `gap`; N/A or "not built" is `na`; blocked/aborted is `blocked`; blue/unclear/needs product input is `uncertain`. When layers disagree, the scenario status is the worst real result among the layers that ran (`fail` > `gap` > `uncertain` > `blocked` > `pass`; `na` layers do not count).
- **Layers.** When the run reports per-layer results, write `layers: [{ "name": "L1-2", "status": "pass", "note": "<observed, short>" }, ...]` using short names consistently (`L1-2`, `L3`, `E2E`, or the run's own labels). Omit `layers` when the run has a single layer. A layer that did not run for a scenario ("—") is left out.
- **Steps.** `steps: [{ "label", "action", "expected", "observed", "result" }]` from the scenario's rows (Action / Expected / Observed / Result). Merge into the plan's steps by position: keep `action`/`expected` from the index, add `observed`/`result`; when the run has more or different steps, use the run's. If the run only has one summary line ("Observed" column), put it in `observed` of a single step, or in `notes`.
- **Evidence.** From `scenarios/<folder>/`: `videos` = `videos/*.mp4` (skip `.webm` when an `.mp4` of the same name exists); `screenshots` = `screenshots/*.png` excluding `raw/` (never listed); `data` = `data/*.json`. Each item `{ "path": "run:scenarios/<folder>/...", "caption"?, "layer"?, "atSec"? }`. Set `layer` from the file prefix: `l1-` is the L1-2 layer, `l3-` is L3, `e2e-` is E2E (use the names of `layers`); no prefix, no `layer`. `caption` from the file name or the run's text (`e2e-s1-02-b-result-expanded.png` gives "E2E result, expanded"). `atSec` only when a file states the video time of a step (`Video @0:42`, `[00:42]`); never estimate. Order by file name.
- **Log excerpts.** For each `.log` or `.md` file in `logs/`, Grep for the scenario id as a word (`S9`, case-sensitive, word boundary; `S1` must not match `S10`) with line numbers. Turn hits into ranges `{ "path": "run:logs/<file>", "from": N, "to": M, "label": "<file>: <first words of the line>" }`: merge hits at most 3 lines apart, pad one line each side, cap a range at 40 lines, keep at most 3 ranges per scenario (the first ones). `from` and `to` are 1-based line numbers within the file, `to >= from`. Do not include a line range for scratch dumps over 5 MB.
- **Gaps.** Run-level `gaps: [{ "id": "G1", "title", "status", "scenarios": ["S16"], "markdown"? }]` from the plan's known-gaps table (id, title) plus the status column of the `## Gaps` table in `steps.md` (for example "Confirmed in server diff; not reachable on PRC"). `scenarios` = ids whose folder or evidence the gap row names, plus scenarios whose results mention the gap id. Set each linked scenario's `links.gaps`. `markdown` holds the evidence cell or a short note.
- **Bugs.** For each folder in `<bugs root>/<slug>/` that this run refers to (the slug, its ticket key or its scenario ids appear in `steps.md`, `logs/*.md` or the plan; when unsure which bugs belong, ask unless `--auto`, and with `--auto` include only the referenced ones), add `{ "slug", "title", "path": "bugs:<slug>/<main>.md", "jira"?, "screenshots": ["bugs:<slug>/screenshots/..."], "scenarios": ["S10"] }`. `title` is the first `#` heading of the main markdown file (the `.md` named like the folder; else the first `.md` that does not start with `opened-` or `jira-ticket`). `jira` is the ticket key from a file named `opened-QI-<n>-jira-ticket.md` (`QI-<n>`), or from the text of `jira-ticket.md` when it holds a key; a `jira-ticket.md` without a key (a draft) gives `"draft"`. `scenarios` = ids named in the bug file or in the run's text. Set each linked scenario's `links.bugs` to the slug. Add `"bugs": "../../bugs"` to `roots` (or the real relative path).
- **Run logs.** `logs: [{ "path": "run:logs/<file>", "label": "<readable name>" }]` for each `.log` and `.md` under `logs/` (skip empty files).
- **Overview panels.**
  - `Results`: `{ "type": "stats", "title": "Results", "span": 2, "items": [{ "label": "Pass", "value": 18, "tone": "good" }, { "label": "Fail", ..., "tone": "bad" }, { "label": "Gap", "tone": "warn" }, { "label": "N/A", "tone": "neutral" }, ...] }` with counts over all scenarios (include Uncertain/Blocked/Planned only when non-zero), plus `{ "label": "Bugs", "value": N }` and `{ "label": "Gaps", "value": N }` when any.
  - `Layer results`: only when the run has layers: `{ "type": "table", "title": "Layer results", "span": 2, "columns": ["Layer", "Run", "Result", "Detail"], "rows": [...] }` from the run summary's layer table.
  - `Run notes and deviations`: `{ "type": "key-value", "title": "Run notes and deviations", "span": 2, "items": [{ "key": "<short title> (S9, S10)", "value": "<one or two sentences>" }] }` from the "Run notes" and deviations of `steps.md` and the layer notes, each with the scenario ids it concerns in the key. Use a `markdown` panel instead when the notes do not split into items.
  - `Scenarios`: `{ "type": "scenario-list", "title": "Scenarios", "span": 2 }`.

## Hashes (so a rerun rewrites only what changed)
`publishedBy.run.hashes` maps a key to a value for every source file read: `steps.md`, `logs/*.md`, `logs/*.log` (text files: `shasum -a 256 <file>`, first 16 hex chars); each file in a scenario folder as `scenarios/<folder>/<relative path>` (media: `size:<bytes>` from `wc -c`, other files: first 16 hex of the sha256); the plan as `plan:test-plan.md`; each bug file as `bugs:<slug>/<file>`. Hash only the files you actually used.

## Steps
0. **Choices.** Skip with `--auto` or `AI_REVIEW_HEADLESS=1`. Otherwise read the run first (steps 2-3), then ask once with AskUserQuestion: "Use these recommendations?" with options "Accept all (Recommended)" and "Let me choose", both with a `preview` that lists: scenarios found, folders mapped and ignored, bugs included, gaps, roots, and whether this is a first publish or a refresh (and which scenarios changed). On "Let me choose" ask only what is unclear: which bugs belong to this run, where the plan or bugs live, how to treat a superseded folder.
1. **Session.** Run
   `ai-review init --kind test-run --run "<run>" --repo "$(git rev-parse --show-toplevel)" --agent-session "${CLAUDE_SESSION_ID}" --format json`
   and note `id` and `url` (the dashboard is `/t/<id>`). It reuses the session of this run folder. If it fails because the run folder is outside the repository, stop and tell the user.
2. **Existing index and hashes.** Read `<run>/test-run.json` if present. Compute the current hashes (see "Hashes"). Changed set: files whose hash differs from `publishedBy.run.hashes`, files new since the last publish, and files that dropped out. First publish (no `publishedBy.run`): everything.
3. **Read and derive.** Read `steps.md`, the layer notes under `logs/`, the plan and the scenario folders as described in "Reading the run". Refresh rule: when a shared text file (`steps.md`, `logs/*.md`, the plan) changed, re-derive `status`, `layers`, `steps`, `notes` and gaps for all scenarios, but replace a scenario only when its derived values differ from the index. Re-scan evidence and log excerpts only for scenarios whose own folder files (or `logs/*.log`) are in the changed set. A scenario that has nothing in the changed set stays exactly as it is. If the changed set is empty, change nothing and say so in step 7.
4. **Build the keys** this skill owns (above), merged over the existing object: scenarios by id (add `evidence`, `logs`, `links` defaults as empty arrays when absent), then the run-level keys and panels, `pages`, `roots.bugs`, `updatedAt`, `publishedBy.run`. Do not change keys you do not own.
5. **Write.** Write the whole object, 2-space indented, to `<run>/test-run.json.tmp` and `mv <run>/test-run.json.tmp <run>/test-run.json`.
6. **Validate.** Run `ai-review run-index validate "<run>"`. Fix errors (same temp file and `mv`) and rerun; read the warnings and fix missing files that are your mistake (wrong path, wrong alias).
7. **Report.** Print the dashboard URL `/t/<id>`, then a table: scenario id, status, layers, evidence counts (videos/screenshots), whether it was changed, added or kept. List the scenarios whose status, steps or evidence changed on a refresh as "verdicts now stale": the reviewer's verdict on them shows as updated since the verdict. Add: folders ignored, bugs included, files that were referenced but missing, and anything you could not map.
